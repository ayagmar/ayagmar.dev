## Context

The site is static pages with one small island (search) and a few page scripts. It should stay fast on a phone without anyone having to remember to check, and a regression should fail the pull request that causes it, with numbers that say where. Tests should be few and each one should catch a bug that can really happen.

### Static budgets

`scripts/budgets.ts` reads the built site and `scripts/budgets.json`, prints one row per page (JavaScript, weight, both budgets) and fails on any problem. A page's JavaScript is every inline `<script>`, every `<script src>` and `modulepreload`, each island's component and renderer, and everything those import, each gzipped (level 9) on its own. Imports are followed from inline scripts too, and a literal dynamic `import()` counts like a static one, since it can run as soon as the page loads. The one exception is a module listed in `onDemand` in `budgets.json` after checking that only a user action loads it: Pagefind's bundle, which the search island imports from its input handler. A file listed in `allowances` is left out of a page's JavaScript and checked against its own cap instead: the theme script, the room clock, the /stats and /uses scripts and the chunks they share, below. A page's weight is its HTML, the stylesheets it links (with their `@import`s and `url()` images), its JavaScript and the images it references, gzip for text and bytes for the rest, fonts excluded.

### Lighthouse

`scripts/lighthouse.ts` serves a build through its own site Worker with `wrangler dev` (local and offline, as e2e does, so `_headers` and the Worker apply), runs `lhci collect` (`@lhci/cli` 0.15.1, Lighthouse 12.6.1) on eight pages, mobile and desktop, three runs each, and takes the median of each metric. Chromium is Playwright's, already cached for e2e, passed as `CHROME_PATH`, run headless with `--no-sandbox`, as Playwright itself launches it (the pages are this site's own). The pages are `/`, `/writing`, `/projects`, `/about`, `/stats`, `/uses`, the largest post and the largest project page (`/writing/*` and `/projects/*` in `budgets.json`: the largest HTML file directly under that directory, so a heavy page cannot hide behind a light one; left out, with a log line, while the build has none, as when every post is a draft). The static budgets check every page, each post and project page included.

Head values must meet these, with simulated throttling (Lighthouse's default mobile profile, and its `desktop` preset):

| Metric         | Mobile   | Desktop  | Why                                                                                                                                                                           |
| -------------- | -------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Performance    | ≥ 0.95   | ≥ 0.95   | A static page with idle islands scores 100 today; 0.95 leaves room for scoring noise, not for a real regression.                                                              |
| LCP            | ≤ 2.0 s  | ≤ 1.0 s  | Below web.dev's "good" 2.5 s, which is measured at the 75th percentile of real visits, because a lab run on a small static page has no excuse. Desktop measures 0.25 s today. |
| TBT            | ≤ 100 ms | ≤ 100 ms | 30 % of the performance score. The islands hydrate when idle or visible; 0 ms today.                                                                                          |
| CLS            | ≤ 0.01   | ≤ 0.01   | web.dev's "good" is 0.1; these pages have no late content, so anything above a rounding error is a bug. 0.003 on some pages today.                                            |
| Accessibility  | 1        | 1        | e2e already requires zero axe violations; Lighthouse's audits must agree.                                                                                                     |
| Best practices | ≥ 0.95   | ≥ 0.95   | 0.96 today: the missing favicon logs a 404 to the console. Adding one brings it to 1.                                                                                         |

**Regressions.** Where the base has the page, a head LCP fails when it is over the base's by more than 10 % and by more than 200 ms on mobile or 100 ms on desktop, and a head TBT by more than 10 % and by more than 75 ms on mobile or 50 ms on desktop. Both conditions, because a ratio alone fires on tiny absolute changes (250 → 280 ms on desktop) and a fixed delta alone on slow pages. The mobile delta is larger than one simulated round trip (150 ms) because LCP on these pages moves by exactly one: Lighthouse sometimes takes a later paint, after the island scripts load, as the largest one, and the simulation then counts their round trip. On the first CI run, with the same site output on both sides, mobile medians were 762 or 912 ms on every page, and the median of three landed on either value for base and head (home 768 → 910, about 911 → 764). Desktop's simulated round trip is 40 ms, inside its 100 ms. A real regression of one mobile round trip, such as a new render-blocking stylesheet, is left to the absolute 2.0 s budget. Scores and CLS have absolute limits only. A regression on the first numbers is a suspicion; it fails only if it holds when the page is measured again (below).

**Mobile TBT.** Mobile TBT had the desktop rule (10 % and 50 ms) until 2026-10-31. In the CI history from 2026-10-29 to 2026-10-31 (240 Lighthouse jobs, 936 mobile page medians), mobile TBT read anything from 0 to 62 ms, and home failed the rule on #73, which changed one e2e test and no page, at 0 → 56 ms, and on #54, a Svelte update, at 0 → 53 ms. #54 changed the JavaScript the site ships, so its number is not known to be noise. The allowance is now 75 ms on mobile, above the 62 ms seen, and the re-measure below decides whatever passes it. It stays, rather than leaving mobile TBT to its 100 ms budget, because the band from 75 to 100 ms is where a real change shows only on mobile: mobile simulates a CPU four times slower than desktop's, so a script that adds one 30 ms task reads as a 120 ms task there (70 ms of TBT) and as 0 ms of TBT on desktop. Desktop TBT read 0 ms in all 944 of its medians and keeps 50 ms. CLS has no regression rule: a floor that clears its third-decimal noise (0.02, say) could never fire under the 0.01 budget. Its budget misses are measured again instead (below).

**Measured again on suspicion.** The base's numbers usually come from the cache, measured on another runner, and mobile LCP moves in simulated round trips of 150 ms, so a cached base that landed a step or two low makes an unchanged page look 300 ms slower: #73 failed on /projects at 1,225 → 1,533 ms, #48 on /stats at 1,401 → 1,679 ms, and ADR 0034 records the same on #39, settled by measuring the base again on the same runner. In the same history, 9 of 272 mobile page pairs against a cached base were 300 ms apart, and 11 of 648 pairs measured in the same job, one side after the other (some of those were real changes). So when a page shows a regression, the job measures that page again on both builds, and only that page: one run of the base, one of the head, in turn, until each has `runs` (three), so a runner that slows during the job slows both sides. The base build is built in every run; its server is started then if the cache meant it was not running. The rule is applied to the medians of those runs, and a regression fails only if it holds there. This applies wherever the base's numbers came from, since a base measured earlier in the same job drifts too. Budgets are absolute and judged on the first head numbers, CLS's apart (below); no other budget is measured again. A page with no regression on its first numbers is not measured again, so a clean pull request costs what it did and each suspected page adds six runs. If the re-measure cannot run (no base build, a server that does not start, a run that measures nothing, a collect that fails twice), the job fails, says why, and keeps the regression from the first numbers; it never passes for lack of numbers. The log prints each re-measured run's LCP, TBT and CLS, for the next time these rules are tuned. A main push re-measures the same way and still keeps its first head medians as the next base, so every cache entry comes from the same method.

**CLS budget misses.** CLS on these pages reads in the third decimal, and now and then lands just over the 0.01 budget on a page nothing changed: #52, a Cloudflare update, failed on desktop /writing at 0.0102, where the other 117 desktop medians of /writing in that history read 0.0015 or 0.0016 (the post read 0.0112 and mobile /writing 0.0213 once each). So a page over its CLS budget is measured again on head alone, three runs in a row (with the base as well, in turn, if the page also looks regressed), and fails only if the median of those runs is still over 0.01. The base is not needed: a budget is absolute. The 0.01 budget is unchanged, and only CLS gets this: a performance, accessibility, best-practices, LCP or TBT budget miss fails on the first numbers. A clean pull request with no CLS miss measures nothing more; a CLS miss alone adds three runs.

`scripts/lighthouse-cli.test.ts` runs the script with a stand-in `lhci` whose numbers each page sets: a page that reads the same on both builds and slows by 40 ms a run passes against a low cached base (it fails if the re-measure measures one side after the other), a real regression still fails, a re-measure that crashes fails with Lighthouse's error, and with no base build a CLS miss of 0.0102 that reads 0.0015 on head measured again passes while one of 0.0515 fails. `scripts/lighthouse.test.ts` replays recorded runs through the re-measure's decision: two local `just lighthouse` runs, each against a cached base of 600 ms so that every page was measured again, gave 15 unchanged pages whose medians landed at most one round trip apart, none failing, and /projects with a 300 KB render-blocking script, 1,512 → 2,858 ms, failing. It also decides the CLS cases on CI's numbers: #52's 0.0102, measured again at /writing's usual 0.0015 and 0.0016, passes; a shift of 0.05 fails; any other budget miss stays as first read.

**A crashed collect.** Lighthouse sometimes crashes on a page it measures fine the next time (the third attempt of #73: `NO_NAVSTART` from the TraceElements gatherer). A failed `lhci collect`, a non-zero exit or a timeout, is run once more; a second failure fails the job, after lhci's own error in the log. The timeout is 30 s per page and run, two runs more for lhci's own retries of a failed run: a run takes about 12 s in CI, and a full collect of 24 runs gets 13 minutes. A collect that hangs twice therefore ends after 26 minutes; even after a head collect of the usual 5 minutes and the job's first half minute of setup, that is about 31 minutes, inside the job's 35, so the job fails with the message and not by being killed. A page that answers 500 fails both times, so the retry costs time and cannot turn a failure into a pass.

**In CI.** `lighthouse` runs when `output` or `perf` paths change (ADR 0018), or when the pull request has the `lighthouse` label (`labeled` is one of the workflow's `pull_request` types, so adding it starts a run). Head is the run's `site-dist` artifact; base is a second checkout of the pull request's base commit (on `main`, the commit before the push), installed and built in the same job with its own `just site-build` in fixtures mode, so both use the same deterministic data. The pages are chosen on head; each is first requested from the base server, and one that answers 404 there (a new largest post, say) is left out of the base run and shown as new. Any answer other than 200 or 404 fails the job. `scripts/lighthouse-cli.test.ts` runs the script with stand-ins for `wrangler` and `lhci` to cover both cases. The job uploads its metrics even when a budget fails.

**Speed.** The job is a matrix of two, `mobile` and `desktop`, running in parallel; `fail-fast` is off so a failure in one still reports the other. Each runs 24 head runs, the base's runs only when the base's numbers are not cached, six more for each page measured again for a regression, and three for a page measured again only for its CLS budget. The job's timeout is 35 minutes: an uncached base with every page measured again is 96 runs. The cache is a small JSON file of medians by URL path, keyed by profile, the commit it measures and a hash of `pnpm-lock.yaml`, `scripts/lighthouse.ts` and `scripts/budgets.json` (a different Lighthouse, measuring code, page list or run count measures again, so base and head always come from the same method). A pull request restores the entry for its base commit and never writes the cache; on a miss it measures the base as before. Only a push to main saves, copying what it measured for its head to the path pull requests restore (a cache's version includes its path) and saving that under its own commit, so the next pull request on that commit finds its base done. A test fails if a save step runs on a pull request or uses another path than the restore. Entries written by pull requests would be readable only by that pull request, and a main entry is written only by a main run. Residual risk, accepted: a pull request whose own edit of the workflow writes a shadow entry in its own cache scope under the expected key could later restore it with the edit removed. Only the owner and their agents push branches, and runs from forks cannot write caches, so no artifact provenance check is built. The cache holds only pages the base was asked about: a head page missing from it is requested from the base server, which is built in every run but started only for those pages; a 404 still shows the page as new and anything else than 200 still fails. A cache that cannot be read counts as empty. The unit of caching is a measured median, so budgets and the regression rule are unchanged.

**The metrics artifact per profile.** Each job uploads `lighthouse-metrics-<profile>`; `lighthouse-comment` downloads them all and renders one comment. The renderer takes the files, validates each as above and merges them, refusing more than one file per profile, a page and profile reported twice and files that disagree on the number of runs. A profile with no artifact (its job failed before measuring) is named in the comment as incomplete and the all-clear line is not written; the `lighthouse` job fails either way.

**The metrics artifact** holds numbers and fixed names only: `{ version: 2, runs, results: [{ page, profile, head, base, over, regressed, remeasured }] }`, six metrics per side, page names from a fixed list, `over` and `regressed` lists of metric names, and `remeasured` null or the medians of the second measurement, `{ base, head }`, on which `regressed` and the CLS entry in `over` were decided; its `base` is null when only head was measured again. Version 2 added `remeasured`; the artifact is written and read in the same workflow run, so no reader of version 1 remains. `scripts/lighthouse-report.js` defines it; the Lighthouse job validates its own output with it before writing.

**The comment.** `lighthouse-comment` is the only job with a write token, and it has `pull-requests: write` and nothing else. It needs `lighthouse`, runs only on same-repository pull requests (on a fork it is skipped and the budgets still fail the gate), checks out no code and uses no action but `download-artifact` for `lighthouse-metrics-*`. The artifact comes from a job that ran the pull request's code and its dependencies, so it is treated as hostile: before rendering, the validator refuses anything over 16 KB unread, anything that is not exactly the schema (extra or missing fields, own `__proto__` keys included), unknown page, profile or metric names, repeated entries, and numbers that are not finite or are outside their range (scores 0–1, times 0–120 s, CLS 0–10). A page measured again has a second row, _re-measured_, with those numbers (head alone when the base was not measured again); the ▲ marks it decided and its CLS ✗ are on that row, and every other ✗ on the first. The comment is built from the validator's fixed labels and formatted numbers only; no string from the artifact reaches the comment or the log. The step then finds the comment by its `<!-- min7-lighthouse -->` marker among comments by `github-actions[bot]` and edits it, or creates one. Because the job checks out nothing, its validator is a copy of `scripts/lighthouse-report.js` in a heredoc in `ci.yml`: plain JavaScript with Node built-ins, run by the runner's own Node. `just lighthouse-embed` writes the copy, and a test fails while it differs from the file. The same tests run the real post step against a stand-in `gh`.

**What the isolation covers.** It protects the write token from hostile artifact data, such as a compromised dependency or build step in the read-only jobs that shapes the metrics file, and it keeps fork pull requests away from any write token. It is not a boundary against a same-repository branch. In a `pull_request` workflow, the job definitions, this one included, come from the branch, so whoever can push a branch can change what this job runs, and can equally add a job that asks for any permission. Same-repository branch authors are therefore trusted: the owner, the only collaborator, and Renovate (ADR 0018 has the trust model). Running the writer from a default-branch workflow would remove that trust, at the cost of a second workflow and binding its artifact to the run and pull request. It is not worth that while no outside contributor can push a branch.

**Not in the gate.** `lighthouse-comment` is listed in `ungated` in `scripts/ci.ts` and is not in the gate's `needs`. The `lighthouse` job is what enforces the budgets; a comment that fails to post (an API error, a rejected artifact) shows as a failed check but cannot block a merge. `continue-on-error` was not used, because a rejected artifact should be visible.

`budgets` and `lighthouse` are ordinary planned jobs in the gate: when the plan expects them they must succeed.

### Changing a budget

Edit `scripts/budgets.json`, the only place the numbers live (the static script, the Lighthouse script and the comment read it or are checked against it), and update the table above with the new number and its reason in the same pull request. The change touches `perf`, so CI runs Lighthouse with the new numbers. Adding a page means a key in `budgets.json` `lighthouse.pages` and a label in `pages` in `scripts/lighthouse-report.js` (then `just lighthouse-embed`); a test fails until both agree.

## Consequences
