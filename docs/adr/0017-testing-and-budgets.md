# 0017. Testing strategy and performance budgets

Status: accepted, 2026-10-26

## Context

The site is static pages with two small islands (search, now playing). It should stay fast on a phone without anyone having to remember to check, and a regression should fail the pull request that causes it, with numbers that say where. Tests should be few and each one should catch a bug that can really happen.

## Decision

### What each layer proves

| Layer           | Where                                              | Proves                                                                                                                                                             |
| --------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Contract tests  | `packages/contracts/test`                          | zod and the exported JSON Schema accept and reject the same payloads; frozen v1 consumers still parse current output (ADR 0008).                                   |
| Worker tests    | `apps/signals/test`, in workerd                    | Push intake rejects bad auth, schemas, replays and oversized bodies; adapters normalize every fixture case; storage keeps only allowlisted fields (ADR 0009–0011). |
| Site unit tests | `apps/site/test`                                   | Feeds, headers and CSP, frontmatter schema, the data reader in both modes, postbuild's inline-code rule, diagrams.                                                 |
| Script tests    | `scripts/*.test.ts`                                | CI plan and gate decisions, the Cloudflare policy, the secret scanners, the budgets and the Lighthouse comment path.                                               |
| e2e             | `apps/site/e2e`, Playwright against `wrangler dev` | Every page at 360 and 1280 px with zero axe violations, no sideways scroll at 320 px, headers and CSP as served, a real search, the now-playing island.            |
| Links           | lychee on `dist/`                                  | No broken internal link; external links alive (ADR 0018).                                                                                                          |
| Static budgets  | `just budgets` on `dist/`                          | The bytes each page ships, fonts, no other origin, image dimensions. Exact and deterministic, so it runs on every build.                                           |
| Lighthouse      | `just lighthouse`, base and head                   | What a browser measures: scores, LCP, TBT, CLS, under Lighthouse's simulated throttling, and that the change did not make them worse.                              |

### Static budgets

`scripts/budgets.ts` reads the built site and `scripts/budgets.json`, prints one row per page (JavaScript, weight, both budgets) and fails on any problem. A page's JavaScript is every inline `<script>`, every `<script src>` and `modulepreload`, each island's component and renderer, and everything those import, each gzipped (level 9) on its own. Imports are followed from inline scripts too, and a literal dynamic `import()` counts like a static one, since it can run as soon as the page loads. The one exception is a module listed in `onDemand` in `budgets.json` after checking that only a user action loads it: Pagefind's bundle, which the search island imports from its input handler. A file listed in `allowances` is left out of a page's JavaScript and checked against its own cap instead: only the theme script, below. A page's weight is its HTML, the stylesheets it links (with their `@import`s and `url()` images), its JavaScript and the images it references, gzip for text and bytes for the rest, fonts excluded.

| Budget                       | Limit                                     | Why                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ---------------------------- | ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| JS, page without islands     | 0 B                                       | A static page needs none; any byte there is an accident (a stray `client:` directive, a snippet). Every page has the search island today, so none is checked against this yet.                                                                                                                                                                                                                                                                                                         |
| JS, page with islands        | 20 KB gzip                                | What the two islands cost: Svelte's runtime (14.3 KB), Astro's island loader (2.4 KB inline) and both components come to 19.8 KB on the home and stats pages and 18.3 KB elsewhere. A new dependency in an island fails it.                                                                                                                                                                                                                                                            |
| Theme script, every page     | 1 KB gzip, on its own                     | `theme.*.js` (ADR 0026) is a blocking classic script in `<head>` that applies the stored Day or Night choice before the first paint; a deferred script would flash the system theme first. It is 0.7 KB, left out of the two JS budgets above as a named allowance in `budgets.json` and capped on its own. It covers one file: a second file matching `theme.*.js` anywhere in the build fails, so growing the script or splitting it fails, and no other file can use the exemption. |
| Page weight, fonts excluded  | 150 KB gzip                               | Home weighs 50.7 KB: HTML, CSS, scripts and both room scenes (12.6 KB night, 10.4 KB day). A browser downloads only the scene for its theme, but both are counted since the check cannot know which. Stats is 26 KB, every other page 24 to 26 KB. 150 KB leaves room for an image per page and still downloads in under a second on a slow mobile connection.                                                                                                                         |
| Fonts, whole build           | 200 KB, woff2                             | Checked apart from page weight so the design knows its envelope. Today 113 KB: the mono (28 KB), the serif roman (44 KB) and its italic (43 KB); home loads the roman and the mono, 72 KB. Fonts are cached across pages, so they count once. Any other font format fails.                                                                                                                                                                                                             |
| Other origins in HTML or CSS | none                                      | Everything is self-hosted: no third-party request can block rendering or see visitors. Any `src`, `srcset`, `poster`, fetching `<link>` (stylesheet, preload, preconnect, icon, manifest…), SVG `href`, CSS `url()` or `@import` with a scheme other than `data:` or a `//` prefix fails. Plain links (`<a href>`, `rel="canonical"`, `rel="me"`) are not requests and pass.                                                                                                           |
| `<img>` width and height     | both, positive whole numbers, every image | Without them the page reflows when the image arrives (layout shift). `auto`, 0 or a negative value reserves no space; units and fractions fail too, since the build never needs them.                                                                                                                                                                                                                                                                                                  |

A reference to a file the build does not contain also fails, since its bytes could not be counted.

The budgets catch accidental growth in the site's own build output, which Vite and Astro write. They are not hardened against hand-crafted evasion, such as a CSS escape (`u\72l()`) that a browser decodes and the checker does not read as `url()`.

### Lighthouse

`scripts/lighthouse.ts` serves a build through its own site Worker with `wrangler dev` (local and offline, as e2e does, so `_headers` and the Worker apply), runs `lhci collect` (`@lhci/cli` 0.15.1, Lighthouse 12.6.1) on seven pages, mobile and desktop, three runs each, and takes the median of each metric. Chromium is Playwright's, already cached for e2e, passed as `CHROME_PATH`, run headless with `--no-sandbox`, as Playwright itself launches it (the pages are this site's own). The pages are `/`, `/writing`, `/projects`, `/about`, `/stats`, the largest post and the largest project page (`/writing/*` and `/projects/*` in `budgets.json`: the largest HTML file directly under that directory, so a heavy page cannot hide behind a light one). The static budgets check every page, each post and project page included.

Head values must meet these, with simulated throttling (Lighthouse's default mobile profile, and its `desktop` preset):

| Metric         | Mobile   | Desktop  | Why                                                                                                                                                                           |
| -------------- | -------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Performance    | ≥ 0.95   | ≥ 0.95   | A static page with idle islands scores 100 today; 0.95 leaves room for scoring noise, not for a real regression.                                                              |
| LCP            | ≤ 2.0 s  | ≤ 1.0 s  | Below web.dev's "good" 2.5 s, which is measured at the 75th percentile of real visits, because a lab run on a small static page has no excuse. Desktop measures 0.25 s today. |
| TBT            | ≤ 100 ms | ≤ 100 ms | 30 % of the performance score. The islands hydrate when idle or visible; 0 ms today.                                                                                          |
| CLS            | ≤ 0.01   | ≤ 0.01   | web.dev's "good" is 0.1; these pages have no late content, so anything above a rounding error is a bug. 0.003 on some pages today.                                            |
| Accessibility  | 1        | 1        | e2e already requires zero axe violations; Lighthouse's audits must agree.                                                                                                     |
| Best practices | ≥ 0.95   | ≥ 0.95   | 0.96 today: the missing favicon logs a 404 to the console. Adding one brings it to 1.                                                                                         |

**Regressions.** Where the base has the page, a head LCP fails when it is over the base's by more than 10 % and by more than 200 ms on mobile or 100 ms on desktop; TBT by more than 10 % and more than 50 ms on both. Both conditions, because a ratio alone fires on tiny absolute changes (250 → 280 ms on desktop) and a fixed delta alone on slow pages. The mobile delta is larger than one simulated round trip (150 ms) because LCP on these pages moves by exactly one: Lighthouse sometimes takes a later paint, after the island scripts load, as the largest one, and the simulation then counts their round trip. On the first CI run, with the same site output on both sides, mobile medians were 762 or 912 ms on every page, and the median of three landed on either value for base and head (home 768 → 910, about 911 → 764). Desktop's simulated round trip is 40 ms, inside its 100 ms. A real regression of one mobile round trip, such as a new render-blocking stylesheet, is left to the absolute 2.0 s budget. Scores and CLS have absolute limits only.

**In CI.** `lighthouse` runs when `output` or `perf` paths change (ADR 0018), or when the pull request has the `lighthouse` label (`labeled` is one of the workflow's `pull_request` types, so adding it starts a run). Head is the run's `site-dist` artifact; base is a second checkout of the pull request's base commit (on `main`, the commit before the push), installed and built in the same job with its own `just site-build` in fixtures mode, so both use the same deterministic data. The pages are chosen on head; each is first requested from the base server, and one that answers 404 there (a new largest post, say) is left out of the base run and shown as new. Any answer other than 200 or 404 fails the job. `scripts/lighthouse-cli.test.ts` runs the script with stand-ins for `wrangler` and `lhci` to cover both cases. The job uploads `lighthouse-metrics` even when a budget fails.

**The metrics artifact** holds numbers and fixed names only: `{ version: 1, runs, results: [{ page, profile, head, base, over, regressed }] }`, six metrics per side, page names from a fixed list, `over` and `regressed` lists of metric names. `scripts/lighthouse-report.js` defines it; the Lighthouse job validates its own output with it before writing.

**The comment.** `lighthouse-comment` is the only job with a write token, and it has `pull-requests: write` and nothing else. It needs `lighthouse`, runs only on same-repository pull requests (on a fork it is skipped and the budgets still fail the gate), checks out no code and uses no action but `download-artifact` for `lighthouse-metrics`. The artifact comes from a job that ran the pull request's code and its dependencies, so it is treated as hostile: before rendering, the validator refuses anything over 16 KB unread, anything that is not exactly the schema (extra or missing fields, own `__proto__` keys included), unknown page, profile or metric names, repeated entries, and numbers that are not finite or are outside their range (scores 0–1, times 0–120 s, CLS 0–10). The comment is built from the validator's fixed labels and formatted numbers only; no string from the artifact reaches the comment or the log. The step then finds the comment by its `<!-- min7-lighthouse -->` marker among comments by `github-actions[bot]` and edits it, or creates one. Because the job checks out nothing, its validator is a copy of `scripts/lighthouse-report.js` in a heredoc in `ci.yml`: plain JavaScript with Node built-ins, run by the runner's own Node. `just lighthouse-embed` writes the copy, and a test fails while it differs from the file. The same tests run the real post step against a stand-in `gh`.

**What the isolation covers.** It protects the write token from hostile artifact data, such as a compromised dependency or build step in the read-only jobs that shapes the metrics file, and it keeps fork pull requests away from any write token. It is not a boundary against a same-repository branch. In a `pull_request` workflow, the job definitions, this one included, come from the branch, so whoever can push a branch can change what this job runs, and can equally add a job that asks for any permission. Same-repository branch authors are therefore trusted: the owner, the only collaborator, and Renovate (ADR 0018 has the trust model). Running the writer from a default-branch workflow would remove that trust, at the cost of a second workflow and binding its artifact to the run and pull request. It is not worth that while no outside contributor can push a branch.

**Not in the gate.** `lighthouse-comment` is listed in `ungated` in `scripts/ci.ts` and is not in the gate's `needs`. The `lighthouse` job is what enforces the budgets; a comment that fails to post (an API error, a rejected artifact) shows as a failed check but cannot block a merge. `continue-on-error` was not used, because a rejected artifact should be visible.

`budgets` and `lighthouse` are ordinary planned jobs in the gate: when the plan expects them they must succeed.

### Changing a budget

Edit `scripts/budgets.json`, the only place the numbers live (the static script, the Lighthouse script and the comment read it or are checked against it), and update the table above with the new number and its reason in the same pull request. The change touches `perf`, so CI runs Lighthouse with the new numbers. Adding a page means a key in `budgets.json` `lighthouse.pages` and a label in `pages` in `scripts/lighthouse-report.js` (then `just lighthouse-embed`); a test fails until both agree.

## Consequences

A pull request that adds weight, JavaScript, a third-party request or a slower page fails with the page and the number. The islands budget has 0.2 KB of headroom on the home and stats pages: a third island or a heavier Svelte needs a decision here first. The theme script has 0.3 KB under its own cap. Page weight and fonts are far from their limits (home 50.7 of 150 KB, fonts 113 of 200 KB). Lighthouse adds a job of an estimated fifteen minutes to output-affecting pull requests (84 Lighthouse runs: seven pages, two profiles, three runs, base and head). `@lhci/cli` brings in a large dependency tree; three transitive packages are overridden to fixed versions and two advisories without a usable fix are ignored by exact version in `osv-scanner.toml` until a set date (ADR 0020).
