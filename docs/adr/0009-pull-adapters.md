# 0009. Pull adapters

Status: accepted, 2026-10-26. Amended 2026-10-26: a fourth adapter, `weather` (Open-Meteo), in ADR 0029; a fifth, `listening-history` (Last.fm), read one year per invocation and scheduled by date, in ADR 0030; a sixth, `monkeytype`, with an optional ApeKey, no redirects followed and the code `upstream_unauthorized`, in ADR 0033. Amended 2026-10-31: projects every 6 hours instead of daily, monkeytype hourly instead of every 6 hours. Amended 2026-11-01: a seventh adapter, `shipping-activity` (repo-pulse daily activity), hourly, kept as daily history, in ADR 0038. Amended 2026-11-07: listening reads only its recent tracks every minute; top artists and the weekly counts have their own cadences and are carried from the stored snapshot, see "Listening's reads". The account is confirmed on Workers Free. Amended 2026-11-11: a featured project can be marked `pull: false` and is not fetched; projects pulls ten repositories and five npm packages, 25 requests, which uses all the room the subrequest test leaves. Amended 2026-11-11: an eighth adapter, `project-events` (GitHub GraphQL), hourly, one request for every featured project, `pull: false` ones included, in ADR 0046; `pull: false` now concerns the projects pull only.

## Context

signals pulls three sources on a cron: Last.fm (listening), the repo-pulse public feed (shipping) and GitHub plus npm (projects). Each upstream fails in its own ways, the Worker runs on the Free plan (10 ms of CPU per cron invocation, 50 subrequests), and no upstream text may reach a log, a response or the site.

## Decision

- One file per adapter in `apps/signals/src/adapters/pull/`, each a `PullAdapter` (`src/adapters/types.ts`): `fetch(env, signal)` does the I/O and returns the raw answers; `normalize(raw)` is pure and returns the snapshot. `pullAdapters` in `index.ts` lists them for the cron runner.
- `fetch` reads every upstream through `getJson` (`http.ts`): one GET with the caller's signal plus its own 5 s timeout, a body cap checked against `Content-Length` and again while streaming (128 KiB for Last.fm, 256 KiB for GitHub and repo-pulse), and the body parsed as JSON or kept as null. It returns `{ status, body }` for any HTTP status, so `normalize` sees 404s and error bodies as data. The raw fixtures record exactly this shape.
- A snapshot built from several requests degrades per part. A part that fails on its own (Last.fm top artists or a weekly count, a project's release or npm downloads, one repository's metadata) becomes `null` in the snapshot. The part a snapshot cannot exist without (Last.fm recent tracks, the repo-pulse feed, GitHub metadata for every featured repository at once) throws.
- Failures throw `PullError` with a `code` from a closed list (`not_configured`, `upstream_unreachable`, `upstream_timeout`, `upstream_too_large`, `upstream_not_found`, `upstream_rate_limited`, `upstream_unauthorized` (a refused key, ADR 0033), `upstream_http_error`, `upstream_error`, `upstream_malformed`, `upstream_incomplete` (an answer its upstream marks incomplete, ADR 0038), and for ADR 0030 `over_budget`, `date_changed` and `in_progress`, the last meaning a part of a pull spread over invocations was read, or that the invocation lost its write to an overlapping one). A refusal (403, 429, Last.fm error 29, Monkeytype's 479) also carries the time from a usable `Retry-After` header, which the runner will not pull before (ADR 0030). Its message is the code and it carries no `cause`, so logging the error cannot leak a URL with the Last.fm key, a token or an upstream body. The cron runner records `error.code`.
- Wire schemas live next to the output schemas in `packages/contracts/src/snapshots/` and declare only the fields the normalizer reads; zod drops the rest. Every normalizer ends by parsing its result with the output schema, which is the allowlist: a field not in the contract cannot be served.
- Timestamps are stored absolute, RFC 3339 in UTC (`2026-10-26T08:53:00Z`). Last.fm's `"26 Oct 2026, 08:53"` and anything like "7 minutes ago" are never stored; the site renders relative times.

Per source:

- **listening** (every 60 s): up to four Last.fm calls for user `min7_` with `LASTFM_API_KEY` (see "Listening's reads" for which, when), each a `POST` with its parameters in a form body. Workers traces record every subrequest's URL and query string, so the key must not be in the URL; Last.fm accepts read methods as `POST`: `user.getrecenttracks` (10 items), `user.gettopartists` (overall, 10), and `user.getrecenttracks` with `limit=1` and `from`/`to` for this week and last week, reading only `@attr.total`. Weeks start Monday 00:00 UTC. Now playing is the first track with `@attr.nowplaying === "true"` and is not repeated in `recent`. Last.fm quirks handled: a list of one is a bare object, an empty list is `[]`, list items are checked one by one so a single odd track or artist is skipped instead of failing the snapshot, errors come as `{ error, message }` even with HTTP 200 (error 6 is an unknown user, 29 the rate limit), images are never read (the site loads nothing from Last.fm), links are kept only when they point to `https://www.last.fm/`.
- **shipping** (every 15 min): `GET https://repo-pulse.ayagmar.workers.dev/public/feed?limit=50` (contract in ADR 0012). Until repo-pulse serves it, the 404 throws `upstream_not_found`, the source never succeeds and the site shows its empty state. Events and star history entries are checked one by one, so one this adapter cannot read is skipped. Events and star history outside the `ayagmar/` account are dropped, and events are sorted newest first whatever order the feed used. Stars on one repository on one UTC day become one entry with the number gained and the latest total.
- **projects** (every 6 hours; daily until 2026-10-31): for each entry of `pulledProjects` (`packages/contracts/src/projects.ts`: the featured projects not marked `pull: false`), `GET /repos/{repo}` and `/repos/{repo}/releases/latest` on api.github.com, and `GET https://api.npmjs.org/downloads/point/last-month/{package}` when the entry names a package. `GITHUB_TOKEN` is optional (a token with no scopes; public data only) and is sent to api.github.com only. A 404 or a private repository drops the project; a renamed repository answers with its new name and URL, which the snapshot shows under the same slug; a release 404 means no release. A pull makes 20 GitHub requests for the current ten, four pulls a day. Without a token GitHub allows 60 requests an hour per IP, and Cloudflare's egress IPs are shared, so a pull may be refused (`upstream_rate_limited`) until a token is set; a token allows 5,000 an hour (https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api). A refused pull keeps the last snapshot, which is called stale only after two days.
- **weather** (every 15 min): one `GET https://api.open-meteo.com/v1/forecast` for the current values over Rabat, body capped at 16 KiB, no key (ADR 0029). Units are checked; a null value stays null; a null weather code throws `upstream_error`; 403 and 429 are `upstream_rate_limited`.
- **listening-history** (by Rabat date, ADR 0030): `user.getInfo` and then one `user.getRecentTracks` page of 200 for today's date in one past year per invocation, as POST forms with the key, until every year since registration is read; the snapshot is written only then. Due at the first trigger of a new date in Rabat, 30 s after each part, 7 hours after a finished pull, and after a failure in 5 minutes backing off to an hour. Bodies capped at 16 KiB and 384 KiB.
- **monkeytype** (hourly, ADR 0033): `GET https://api.monkeytype.com/users/personalBests?mode=time`, then `?mode=words`, with `MONKEYTYPE_APE_KEY` in the `Authorization` header, `redirect: 'manual'` so the key never follows a redirect, body capped at 128 KiB. The key is optional; without it nothing is asked. 401, 403 and 470 to 472 are `upstream_unauthorized`, 429 and 479 `upstream_rate_limited`.
- **shipping-activity** (hourly, ADR 0038): `GET https://repo-pulse.ayagmar.workers.dev/public/activity?days=400` on the first pull of a UTC date and `?days=35` on the others, body capped at 512 KiB. An answer marked `complete: false` is asked for once more at once; a second one is `upstream_incomplete`, tried again 2 minutes later. Otherwise all or nothing: a window that is not exactly the 35 or 400 days ending on `generatedAt`'s UTC date, a day whose counts are not its repositories' sums, or days that contradict `since` are `upstream_malformed`. Days are checked by a hand-written reader held to the contract, since zod in workerd is slow over 400 of them. Its days are merged with the stored ones and written in the snapshot's batch; it waits out the first 15 minutes of a date in Rabat.
- **project-events** (hourly, ADR 0046): one `POST https://api.github.com/graphql` with an alias per featured project, for its 10 newest releases and 20 most recently updated merged pull requests, body capped at 512 KiB. Needs `GITHUB_TOKEN`; without it `not_configured` and no request.
- The featured list is in `contracts`, not in signals, because the site joins posts to projects by `slug`. Every project in the snapshot carries its slug.

Connections: Workers keeps at most six subrequests waiting for response headers per invocation and queues the rest, and each request's 5 s timeout starts when `fetch` is called, queued or not. `projects` therefore runs its requests through `runLimited` with six at a time, so a slow GitHub does not time out the last batch while it waits. The limit is per invocation: the cron runner should run adapters one after another, not all at once.

Bounds: listening makes 1 subrequest in a usual minute and at most 4 (6 with its day reads, ADR 0038), shipping 1, shipping-activity at most 2, weather 1, monkeytype 2, project-events 1, listening-history at most 2 (`test/listening-history.test.ts` counts them), projects 2 per pulled repository plus 1 per npm package (25 for the current ten, with five packages). Workers Free allows 50 per invocation and counts each redirect hop, and a renamed repository costs two, so `test/pull-fetch.test.ts` counts each adapter's real requests and fails when twice that number passes 50. That leaves no room for another pulled project: one more needs another marked `pull: false`, which suits a project whose releases or packages say nothing about the repository as a whole (agents-skills publishes one per skill), or that has neither (kipple and dotfiles). The cron runner runs one adapter per invocation (see CPU below). Every body is capped, and lists are capped at 10 tracks, 10 artists and 50 events.

CPU: the account is on Workers Free (owner, 2026-11-07), which allows 10 ms of CPU per cron invocation. Production's cron ran at a median of 15 ms and a p99 of 33 ms in early November with no invocation failing, which is above the limit and not something to rely on. Measured in Node on a desktop on 2026-10-26: the first `normalize` of each adapter in a fresh process takes 2.4 ms (projects) to 7 ms (listening, shipping), mostly zod building its schemas; later calls take 0.3 to 0.5 ms. zod cannot use its eval-based fast path in workerd, so the cold cost there may be higher. Three cold adapters in one invocation would exceed the limit; one fits, with little margin on a cold isolate. The cron runner runs one adapter per invocation (`src/cron/run.ts`) and records its attempt before it runs (ADR 0038), so one cut off by the limit waits its interval instead of being picked at every run; and the CPU time of each cron invocation should be checked in Workers Observability after the first deploy. `just signals-cpu` measures an invocation per adapter in a local workerd (ADR 0030).

### Listening's reads

Amended 2026-11-07. Listening is 1,200 of about 1,440 daily cron runs, and three of its four calls fetched numbers that barely move in a minute. The owner accepted that top artists and the weekly counts lag a little.

| Part                | Read                                        | Why                                                                                     |
| ------------------- | ------------------------------------------- | --------------------------------------------------------------------------------------- |
| Now playing, recent | Every pull                                  | What the page polls for                                                                 |
| This week's count   | First pull of each 15-minute slot, from :07 | The source's `stale` threshold, so the number lags no more than the page already allows |
| Top artists         | First pull of each hour, from :30           | All-time totals move by a few plays an hour                                             |
| Last week's count   | At the rollover                             | It is closed. Read once, or twice if the first pull lands in the settling minute        |

- **Slots.** A part is due when the stored `fetchedAt` is in an earlier slot than now. That needs no new state, so a restart changes nothing, the snapshot's shape stays frozen, and older Workers read and write the row as before. The offsets keep the two reads apart and out of the first five minutes of an hour, so the pulls that read days (ADR 0038) grow no heavier.
- **Carrying.** The pull reads the stored snapshot and checks it with `listeningSnapshotSchema`. A part not read, or read and failed, keeps its stored value, and a failed read waits for its next slot. A part stored as null is read at every pull. With no snapshot, or one of another shape, every part is read and nothing is carried. A whole pull that fails stores nothing, so what was due stays due.
- **The week.** Weeks start Monday 00:00 UTC, which is also Rabat's since 2026-09-20. A week count carries only if `fetchedAt` is at least a minute past this week's start. The minute covers a pull that began on Sunday and stored its old count seconds into Monday; the runner gives up on a fetch after 20 seconds. A failed read at the rollover leaves null, shown as `unknown`, and is retried at the next pull: an old week's number is never shown as this week's.
- **Refusals.** While `days:listening` holds (ADR 0038) the slow parts are not asked. A `Retry-After` on a slow part extends that hold, since the recent tracks' success clears the source's own cooldown. The recent tracks are never held by it; a refusal of those stops the source as before. A rollover during a hold leaves null.
- **Honest times.** `fetchedAt` and `stale` say when the recent tracks were read, which is what they always decided. A carried number can be older: normally by up to 15 minutes, or an hour for top artists. If only the slow reads keep failing, it stays as it was until the week ends (top artists, until they recover) with `stale` false. The owner chose that over clearing the number. Each failed read, by the same test `normalize` uses, logs `listening part unread` with the parts' names, so Workers Logs shows what the envelope does not. Neither time was changed to track these parts: that would need a new field, and a stale flag for one tile would hide a working now playing.
- **Last week's repair.** The first pull past Monday 12:15 reads the count again, and the higher of the two stands, as a finished week does not shrink (the day merge's rule, ADR 0038). That takes in the morning's late scrobbles and a one-off low answer at the rollover, for one more call a week; a once-a-day read would cost six more and only adds scrobbles synced later in the week.
- **Limits.** Scrobbles that arrive after Monday's repair miss last week's count until it rolls off, and a repair that fails or falls in a hold is not retried. The hourly day reads still count late scrobbles per day for a day after the date.
- **Cost.** About 1,320 Last.fm calls a day at 1,200 pulls, with last week's count adding 2 or 3 a week, down from 4,800 (1,560 down from 5,760 at one pull a minute), plus the day reads, which are unchanged. D1 gains one row read per pull. `just signals-cpu`, four interleaved runs on a busy machine, medians over the baseline: 8.2 cold / 3.4 warm before, 8.7 / 3.7 after, which is within this bench's noise. The bench answers from memory and runs D1 in process, so it charges the new query and credits little for the three requests saved; with the query removed the same runs gave 7.3 / 2.6. CPU in production is the number to read after a deploy.

## Consequences

Adding a source is one adapter file, its schemas in `contracts` and its fixtures. The cron runner (signals intake PR) does not know any upstream: it calls `fetch`, then `normalize`, and records either the snapshot or `PullError.code`. `LASTFM_API_KEY` is in `secrets.required` of `wrangler.jsonc`, so a deploy fails without it; `GITHUB_TOKEN` and `MONKEYTYPE_APE_KEY` are optional and not declared. `readSecret` reads them at run time and treats empty as unset.
