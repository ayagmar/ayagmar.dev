# 0046. Each project's log from GitHub

Status: accepted, 2026-11-11. Amends ADR 0008 (a source added within v1), ADR 0009 (an eighth adapter; `pull: false` covers the numbers pull only) and ADR 0010 (a source, a route, listening's first gap after a cold start).

## Context

`/projects/<slug>` showed a "Recently shipped" log drawn from `/v1/shipping`, which holds the 50 newest public events across all of the owner's repositories. On 2026-11-11 those covered about 41 hours, 32 of them runnerd's, so 2 of 14 project pages had a log, and a project's release left its page within hours of a busy day elsewhere.

Each featured project's page should show its own latest releases and merged pull requests, as far back as they go, however busy other repositories are. Three ways were weighed:

|                           | Accumulate from the shipping pull in D1            | A per-repository feed from repo-pulse               | GitHub's GraphQL API         |
| ------------------------- | -------------------------------------------------- | --------------------------------------------------- | ---------------------------- |
| History before the change | None: the feed holds 100 events within 90 days     | Back to 2026-10-03, when repo-pulse began recording | All of it, on the first pull |
| State in signals          | A table, pruning, dedupe and ordering across pulls | One snapshot                                        | One snapshot                 |
| Work elsewhere            | None                                               | A new public route in repo-pulse                    | None                         |
| Subrequests               | 0                                                  | 1 or 14                                             | 1                            |

The first leaves the quietest projects empty, and the second cannot go back before repo-pulse existed. GitHub has every release and merge, and one GraphQL request can ask for all featured repositories at once.

## Decision

**A source, `project-events`.** `apps/signals/src/adapters/pull/project-events.ts` sends one `POST https://api.github.com/graphql` an hour with an alias per featured project, `pull: false` ones included, since here a repository is one more alias and not more subrequests. For each it asks `nameWithOwner`, `isPrivate`, the 10 newest releases by creation and the 20 merged pull requests updated most recently. `GET /v1/project-events` serves the snapshot as a contract envelope (`project-events.output.json`, frozen in `test/frozen/v1/`): per project, `{ slug, repo, events }`, where each event has exactly the shape of a `/v1/shipping` release or merge. It is stale after 6 hours. No migration: the snapshot is one row in `snapshots`, replaced whole by each pull, so nothing accumulates, and nothing needs pruning or ordering across pulls.

**The token.** GitHub's GraphQL API answers no anonymous request, so `GITHUB_TOKEN` becomes required for project logs. It stays optional for the numbers pull and is not in `secrets.required`. Without it the pull records `not_configured` and asks nothing; a refused or expired token is `upstream_unauthorized`. The token is the fine-grained, public-only one docs/deploy.md describes, which reads no private repository; it goes to `api.github.com` alone, with redirects not followed. A pull costs 1 point of the token's 5,000 an hour, which it shares with anything else the token is used for.

**Which repositories are named.** Only a repository GitHub answers with `isPrivate: false` and a name under `ayagmar/`. A repository GitHub reports as not found (deleted, or private to a public-only token), one it calls private, and one moved to another account are left out. A rename is followed: GitHub answers with the new name, which the entry carries under the same slug. Any other repository without an answer (a null alias with another error, an alias missing, a shape that does not match) fails the whole pull and stores nothing: a passing GitHub error on one repository must not read as that repository going private, hide its log on every open page and be baked into the next site build. The last snapshot stays, as for every failed pull, so a repository made private during a run of failures stays named until the next success.

**What a log holds.** Per project, the newest 10 releases and the newest 10 merged pull requests, each kind chosen on its own and the two merged by date for display, newest first; so releases stay visible on a repository that merges all day (on 2026-11-11 runnerd's 20 newest events were all merges). Drafts are never listed; prereleases are, as `/v1/shipping`'s log listed them. Pull requests opened by dependency bots are left out, decided in signals so the contract carries only what is shown: the author's login, lowercased, is `dependabot`, `dependabot[bot]`, `renovate` or `renovate[bot]` (GraphQL names a bot without `[bot]`, REST and the web with it). A deleted account's pull request (`author: null`) is listed. The login is read for that and never stored or served. The same URL twice is listed once; equal times are ordered by URL.

**No gaps.** GitHub orders merged pull requests by update, not by merge. The 20 most recently updated hold every merge after the 20th's `updatedAt`, since a merge sets `updatedAt` to at least `mergedAt`, and an arbitrary few before it: an old pull request cross-referenced today takes a place. So each connection that returns a full page has a frontier, the oldest `updatedAt` of its nodes (bots' and unreadable ones' places included), and a merge older than it is dropped. The log can be shorter than 10 merges, never missing one between two it shows. Releases are asked in creation order, and the frontier is the oldest `createdAt`; a release created before the 10th and published after it is the one gap GitHub's order cannot show. A short page is everything there is.

**Reading the answer.** zod reads the answer, its errors one by one, and each alias. Release and pull request nodes go through a hand-written reader (`readReleaseNode`, `readMergedPull`), as ADR 0038's day reader does: zod per node cost milliseconds in workerd. `test/pull-normalize.test.ts` holds the reader to `githubReleaseNodeSchema` and `githubMergedPullSchema` on every fixture node and on a case at each check's edge. A node that does not match is skipped. The snapshot still ends in `checkSnapshot`, the allowlist. HTTP 401 is `upstream_unauthorized`; 403 and 429, or a 200 with no data and a `RATE_LIMITED` error, `upstream_rate_limited`; other statuses fail as every pull's do.

**Schedule.** Hourly, after the first 15 minutes of a date in Rabat as `shipping-activity` waits (ADR 0030's midnight is unchanged). With eight pulled sources, listening's first gap after a cold start is 8 minutes, then at most 3.

**The site.** The project page and its text copy draw the log from the project's own entry (`projectEvents` and `projectLog` in `apps/site/src/lib/project-panel.ts`), at build and in the browser, which asks `/v1/project-events` every 30 minutes while the page is visible. A newer answer that leaves the project out hides the log. `/stats`, the room and `/room` keep reading `/v1/shipping`.

## Consequences

- 13 of the 14 featured projects show a log from the first pull; headroom has neither releases nor merged pull requests.
- A release or merge shows within about an hour, where the shipping feed showed it within 20 minutes.
- A repository made private leaves the snapshot at the next successful pull, open pages within 30 minutes of that, and built pages at the next site build, as ADR 0012 says of the shipping feed.
- An expired or missing `GITHUB_TOKEN` freezes every log at its last snapshot, which turns stale after 6 hours. `/v1/health` shows it as `lastErrorCode` for `project-events`.
- A site built before signals has a snapshot shows no log in its HTML and text copies; the browser fills it from the first answer. Rebuild the site once after the first pull.
- Moving the numbers pull to GraphQL would free 19 of its subrequests; that is a separate change.
